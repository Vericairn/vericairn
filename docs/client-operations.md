# Cancellable client operations

Every `IEstateApi` operation has an `Async` counterpart with the same arguments and result, followed by an optional `CancellationToken`. The synchronous signatures, argument defaults, response shapes, exception types and messages remain unchanged. Synchronous calls retain their original HTTP timeouts and do not pass through the async failure mapper. `VericairnClient` also provides asynchronous shutdown, pairing, certificate rotation, runtime identity and OpenAPI requests.

The SDK awaits transport I/O and response bodies without capturing the caller's synchronization context. The default interface implementations adapt embedded synchronous runtimes on a worker thread. Cancellation stops waiting for an embedded operation; it cannot interrupt synchronous runtime code that is already executing. The embedded runtime retains its resources until that work finishes, even if the caller disposes it after cancelling. Consumers should await the asynchronous methods and keep observable UI state on the UI thread.

Each async operation has its own deadline covering connection, request and complete response, including parsing. FIX-28 checks elapsed monotonic time as well as timer cancellation, so a late successful response cannot evade an expired deadline. Interactive reads normally have 30 seconds. Checks, context preparation, handoffs, object transfers, exports, upgrades, document checks, harness qualification, run preparation and release operations have 15 minutes. These deadlines bound client observation, not the lifetime of an agent run. `VericairnClient.OperationTimeout` can override the deadline by operation name. The existing local-network timeout argument overrides operation deadlines for that client. The async HTTP transport's global timeout is disabled so it cannot prematurely end a longer operation.

`ClientCancelledException` identifies caller cancellation; `ClientTimeoutException` identifies a deadline. `ClientUnavailableException` identifies a lost or unusable transport response, including an unrelated transport cancellation. Their `OutcomeUnknown` property is independent of the reason observation stopped. A write that may have reached the runtime stays uncertain, including when its response is truncated, unreadable or a server error: cancellation is not rollback, a timeout is not evidence of failure, and no client automatically retries it. Reconcile the original operation with runtime records before considering another effect. Cancellation already requested before invocation does not dispatch a request and has no uncertain effect. Read-only POST operations, such as handoff comparison, do not become effects merely because of their HTTP method.

`ClientRefusedException` identifies a definite refusal in an async request, with its original diagnostic and `OutcomeUnknown` set to false. TLS screening, failed authentication or runtime identity proof, a pairing refusal, and a runtime problem explicitly saying `refused` or `denied` cannot become unavailable or uncertain. This includes a refusal returned with HTTP 503 because the runtime cannot keep a write's device ledger. An HTTP client-error rejection whose diagnostic is unreadable keeps its refusal status. A server error without a usable refusal, or a successful HTTP response with an empty or contradictory write outcome, remains uncertain for an effect. A connection that could not be opened has no uncertain effect.

`ClientFailure` supplies the shared boundary vocabulary and messages: `cancelled`, `timed-out`, `unavailable` and `refused`. An uncertain effect appends an instruction to reconcile the original operation before retrying. A normal response, including a structured refusal, keeps its existing representation.

The MCP registry passes the request token through admission checks and every API call. `McpServer.RunAsync` keeps reading while tools run, accepts `notifications/cancelled` with the original `requestId`, and serializes complete response lines. A cancellation targets that request only. Interrupted tools return an error result with the shared message; an interrupted tool listing returns a JSON-RPC error. Pings remain available while a tool is pending. Server cancellation settles active requests and stops waiting even if its input reader cannot interrupt a blocking read. The synchronous registry and server entry points remain available for existing callers.

Workbench awaits application commands on its UI context while transport and embedded work yield. Its status bar shows `busy`, `cancelled`, `timed-out`, `unavailable` or `refused`; Cancel and Escape stop the active observation, and refresh is disabled while a command runs. Navigation and draft editing remain available. Interrupted observations mark retained views as cached, and late responses cannot replace them. A session notice preserves uncertain effects across subsequent successful refreshes. An editor with an uncertain effect disables further submission; observing an existing release remains available for reconciliation. A refused effect leaves the editor available without adding uncertainty. A confirmed write keeps its receipt if a subsequent refresh is interrupted. Runtime lifecycle commands also accept cancellation and deadlines; stopping their child process does not claim to reverse a service change. Saving a hand-over writes a temporary file and moves it into place only after the complete write, so cancellation cannot leave a partial package at the chosen destination.

The [generated CLI outcomes reference](cli-client-outcomes.md) specifies the diagnostic and exit code for each interrupted request. CLI diagnostics go to standard error without replacing the normal JSON response. The command boundary binds Ctrl+C and a caller token to SDK operations, including MCP serving. Worker following and runtime serving preserve their existing explicit-stop behavior.

Pairing, adding a connection and probing a connection also expose asynchronous cancellation. The asynchronous probe propagates interruption to its caller; its synchronous counterpart retains the existing completed `unavailable` or `partial` observation on a deadline. Pairing becomes a possible effect when confirmation is dispatched: a silent handshake or interrupted challenge cannot admit a device. A pairing whose confirmation is lost remains an uncertain effect. A confirmed refusal remains definite even after confirmation was dispatched.

The existing documentation tool generates both the “Interrupted client requests” section in the full CLI reference and its `cli-client-outcomes.md` excerpt from `ClientFailure`. Both pages also carry “Stored records awaiting companion recovery” from the retained build input. `docs check` requires that section in a set that declares the client-outcomes page; the build tool's comparison checks the complete generated bytes. After an offline or otherwise permitted restore, generate an unfrozen set with:

```sh
dotnet run --project tools/Vericairn.DocsTool --no-restore -- generate --out artifacts/reference --documents docs/releases/documents.json
```

Keep `docs/cli-client-outcomes.md` in agreement with both generated sections when updating this living reference. Generate into ignored build output and leave frozen release sets and their checksums unchanged.
