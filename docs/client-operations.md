# Cancellable client operations

Every `IEstateApi` operation has an `Async` counterpart with the same arguments and result, followed by an optional `CancellationToken`. The synchronous signatures, argument defaults and response shapes remain available. `VericairnClient` also provides asynchronous shutdown, pairing, certificate rotation, runtime identity and OpenAPI requests.

The SDK awaits transport I/O and response bodies without capturing the caller's synchronization context. The default interface implementations adapt embedded synchronous runtimes on a worker thread. Cancellation stops waiting for an embedded operation; it cannot interrupt synchronous runtime code that is already executing. Consumers should await the asynchronous methods and keep observable UI state on the UI thread.

Each operation has its own deadline covering connection, request and complete response, including parsing. Interactive reads normally have 30 seconds. Checks, context preparation, handoffs, object transfers, exports, upgrades, document checks, harness qualification, run preparation and release operations have 15 minutes. These deadlines bound client observation, not the lifetime of an agent run. `VericairnClient.OperationTimeout` can override the deadline by operation name. The existing local-network timeout argument overrides operation deadlines for that client. The HTTP client's global timeout is disabled so it cannot prematurely end a longer operation.

`ClientCancelledException` identifies caller cancellation; `ClientTimeoutException` identifies a deadline. `ClientUnavailableException` identifies a lost transport response. Their `OutcomeUnknown` property is independent of the reason observation stopped. A write that may have reached the runtime stays uncertain: cancellation is not rollback, a timeout is not evidence of failure, and no client automatically retries it. Reconcile the original operation with runtime records before considering another effect. Cancellation already requested before invocation does not dispatch a request and has no uncertain effect. Read-only POST operations, such as handoff comparison, do not become effects merely because of their HTTP method.

`ClientFailure` supplies the shared boundary vocabulary and messages: `cancelled`, `timed-out` and `unavailable`. An uncertain effect appends an instruction to reconcile the original operation before retrying. A normal response, including an explicit refusal, keeps its existing representation.

The MCP registry passes the request token through admission checks and every API call. `McpServer.RunAsync` keeps reading while tools run, accepts `notifications/cancelled` with the original `requestId`, and serializes complete response lines. A cancellation targets that request only. Interrupted tools return an error result with the shared message; an interrupted tool listing returns a JSON-RPC error. Pings remain available while a tool is pending. The synchronous registry and server entry points remain available for existing callers.

Workbench awaits application commands on its UI context while transport and embedded work yield. Its status bar shows `busy`, `cancelled`, `timed-out` or `unavailable`; Cancel and Escape stop the active observation, and refresh is disabled while a command runs. Navigation and draft editing remain available. Interrupted observations mark retained views as cached, and late responses cannot replace them. A session notice preserves uncertain effects across subsequent successful refreshes. Runtime lifecycle commands also accept cancellation and deadlines; stopping their child process does not claim to reverse a service change.

The [generated CLI outcomes reference](cli-client-outcomes.md) specifies the diagnostic and exit code for each interrupted request. CLI diagnostics go to standard error without replacing the normal JSON response. The command boundary binds Ctrl+C and a caller token to SDK operations, including MCP serving. Worker following and runtime serving preserve their existing explicit-stop behavior.

Pairing, adding a connection and probing a connection also expose asynchronous cancellation. The asynchronous probe propagates interruption to its caller; its synchronous counterpart retains the existing completed `unavailable` or `partial` observation on a deadline. A pairing whose confirmation is lost remains an uncertain effect.
