# FIX-173: changes merge reads a failed_checks removal as a failed check

## docs/limitations-and-platforms.md

### In "Checked changes and operator actions", in the paragraph beginning "Checked pushes need an installed Gitleaks scanner", after the sentence ending "so a clock far from the host's leaves more merges uncertain."

> From 0.9.5 (FIX-173), the provider reads those reasons as GitHub sends them: the words its pull request timeline records, such as
> `failed_checks`, `merge_conflict` and `merged`, and the upper-case reasons GitHub documents for its `dequeued` webhook. A reason
> it does not know, such as one GitHub adds later, reads as a removal that is not a failure, with the reason shown. A removal
> because the queue merged the change leaves the merge uncertain until its pull request reads merged.

## docs/api-compatibility-0.9.5.md

### Under the 0.9.5 changes

> ## The merge queue's removal reasons as GitHub sends them (FIX-173)
>
> No route, interface member, protocol type, record type or field changes, and no public member is added or changed. Behavior:
> `GitHubPullRequestProvider.ObserveQueue` (`Vericairn.Providers.GitHub`) reads a removal whose reason is `failed_checks`, the word
> GitHub's timeline records for failed checks, as `failed`, where it read `removed`; and one whose reason is `merged`, `MERGE` or
> `ALREADY_MERGED`, which GitHub records when its queue merges the pull request, as `absent`, keeping its `Reason` and `RemovedAt`,
> where it read `removed`. `MergeQueueObservation`'s `absent` (`Vericairn.Runtime`) covers such a removal: the host reports no
> removal that took the pull request out unmerged. A pull-request observation may now record the target fact `queue` as `absent`
> beside `queueReason` and `queueRemovedAt`. `changes observe` settles a queued merge removed for failed checks as the queue's
> failure, and leaves one the queue merged `uncertain` until its pull request reads merged, where a pull request that did not read
> merged yet settled it as a `known-failure`.
