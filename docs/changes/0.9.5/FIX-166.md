# FIX-166: Routed flow steps carry typed permitted paths

## docs/operator-guide.md

### In "Runs of a flow (0.9.2)", after the paragraph beginning "A run is a goal whose plan names a flow"

> From 0.9.5 (FIX-166), routing creates a step's permitted changes from its declared paths, the goal's repeatable `--flow-path`
> patterns and the `path:` entries of the run's work order. The brief's patterns must fit each supplied list. Choose compatible
> lists and declare a narrower pattern where they overlap. A run that leaves an agent work step without an interpretable pattern is refused at
> proposal and activation with `flow.permitted-paths`. `goal step --check` previews the next step and its permitted changes
> without signing, recording or dispatching.
>
> The work order's `path:` entries are read from the revision the goal's plan names and from every later revision of it, so a
> later revision narrows a run's paths and never widens them. When the named revision has no `path:` entry, a later revision's
> entries grant nothing. To widen them, or to give them first, revise the goal to name the new revision. A later revision that
> drops every `path:` entry withdraws nothing: the run keeps the named revision's paths until the goal names another. A step a
> person carries, or a reserved one, needs no pattern, and its brief carries the work order's prose, never a pattern. A run
> started directly on a step's held assignment is refused with `flow.permitted-paths` unless its brief is within the step's
> current paths. A standing agent's steps keep their own briefs.

## docs/api-v1.md

### After the table containing `POST /v1/goals/{id}/activate`

> From 0.9.5 (FIX-166), the goal proposal body may provide repository-relative worker patterns in `plan.flow.paths`. The
> runtime combines that list with the step's `paths` and explicit `path:` entries in the run's work-order scope. Each supplied
> list limits the routed assignment's `brief.permittedChanges`. Proposing or activating a goal refuses with
> `flow.permitted-paths` when its agent work step would have no permitted path pattern. For a flow run, `POST /v1/goals/{id}/step/check`
> previews the next step and `GoalStepResponse.permittedChanges` carries the patterns for its routed assignment. The preview
> signs, records and dispatches nothing. The SDK sends `GoalStepRequest.Check` to this preview route through its existing goal
> step methods. An older runtime returns HTTP 404 for the preview route.
> A stored run with a path refusal shows it in the goal view's `flow.pathRefusals` and in status's `flowPathRefusals`, which
> also supplies the refusal shown in Workbench and Remote.

## docs/api-compatibility-0.9.5.md

### Under the 0.9.5 changes

> `GoalStepRequest.Check` and `GoalStepResponse.PermittedChanges` are additive. The SDK uses the new
> `POST /v1/goals/{id}/step/check` route when `Check` is set.
> From 0.9.5, a flow run with an agent work step lacking a permitted path is refused at proposal or activation with
> `flow.permitted-paths`. A stored run's path refusals appear in its goal view and status when present.
