# ID-19: Acknowledge an unwitnessed record deletion

## docs/operator-guide.md

### In "History checkpoints (0.9.2)", after the paragraph beginning "What a removal leaves, and what anchors decide"

> **Acknowledging a deletion no checkpoint witnessed (0.9.5).** The root operator can acknowledge a Git deletion in a
> repository-synced estate that has adopted history checkpoints. Upgrade every participating reader to 0.9.5 or later before
> writing the acknowledgment. Use a complete clone whose local main line contains the deletion.
>
> 1. Run `vericairn estate check` and use the full commit and path from `history.deleted-in-git`. If the check names a merge,
>    you may name the branch's deleting commit when the merge reaches it through a parent that already lacks the path and both
>    commits show the same record id and content hash deleted at that path, and no commit between them adds the path back. A
>    record restored after the acknowledged deletion and deleted again, in a merge or not, is a new deletion and warns.
> 2. Read the deleted record from a parent of the commit you chose that still held the file. Use
>    `git show '<parent>:<record path>'` to save a copy outside `records/`. Read its `id` and use its verified content `hash`, the
>    value computed by `vericairn records hash <file>`. The file must parse as a record and its declared hash must agree with the
>    computed hash. In the new body, set `trigger` to `manual` and add a `removed` entry with the `id`, `hash`, full `commit` and
>    a non-blank `reason`. Sort multiple entries by id.
> 3. Run `vericairn estate checkpoint --check --json` to get the current `heads`, in full, and the expected counts. Put the
>    heads' `{id, hash}` pins in `previous`, sorted by id. Read the inventories of those heads and their predecessors to find
>    what they still witness after acknowledged witnessed removals. For each present record the heads do not witness, write a
>    line with its path relative to `records/`, a space and its content hash. Sort by record id, use UTF-8 and end each line
>    with a line feed. Split at line boundaries to keep each inventory object at most 8 MiB. Store each object as
>    `objects/<lowercase SHA-256 hex>` and list its `sha256:<hex>` hash in `inventory`, in line order. Use `[]` if there are no
>    new records to witness.
> 4. Combine the records still witnessed by the previous heads with the new inventory, one `{hash, id}` pair per record. Set
>    `records` to the number of pairs and `recordSetHash` to `sha256:<hex>` of the canonical UTF-8 JSON array of those pairs,
>    sorted by id, with keys in `hash`, `id` order and no whitespace or final newline. The deleted record contributes no pair.
>    See the [checkpoint entry format](record-format-v3.md#history-checkpoints-092).
> 5. Write the body with `vericairn records new history-checkpoint --by <root operator> --body <checkpoint-body.json>` and sign
>    with an admitted device that requires your presence. Run `vericairn estate check` again. It reports `history.deleted-in-git`
>    as acknowledged, naming the commit it found and the acknowledging checkpoint. It also names the checkpoint's commit if
>    it differs. An entry without the root operator's required presence signature is reported as `history.git-removal-author`.
>    Other unwitnessed deletions still warn, including a later separate deletion after restoring the same record.
