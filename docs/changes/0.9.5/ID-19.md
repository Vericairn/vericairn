# ID-19: Acknowledge an unwitnessed record deletion

## docs/operator-guide.md

### In "History checkpoints (0.9.2)", after the paragraph beginning "What a removal leaves, and what anchors decide"

> From 0.9.5 (ID-19), the root operator can acknowledge an unwitnessed record deletion in a repository-synced estate. In the next checkpoint's `removed` list, include the absent record's `id`, its content `hash` from the deleting commit's parent, the full deleting `commit` and a non-blank `reason`. Write the checkpoint with `vericairn records new history-checkpoint --by <root operator> --body <checkpoint body.json>` and sign with an admitted device that requires your presence. The checkpoint follows every current head and contains the current inventory, count and record set hash. Use the commit printed by `estate check`. If it prints a merge, you can also use the branch's deleting commit when both commits are on the local main line's reachable history and both deleted the same record id and content hash at the same path. `estate check` then reports `history.deleted-in-git` as acknowledged for that path and names the checkpoint. Other unwitnessed deletions still warn. See the [checkpoint entry format](record-format-v3.md#history-checkpoints-092).
