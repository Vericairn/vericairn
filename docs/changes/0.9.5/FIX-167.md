# FIX-167: Claude Code uses a provisioned setup-token sign-in

## docs/operator-guide.md

### In "18. Routing, asks and the worker", after the paragraph beginning "The person must hold the operator role"

> From 0.9.5 (FIX-167), an operator can generate a headless sign-in with `claude setup-token` and import it using
> `worker configure --launcher claude-code --import-setup-token --account-type pro` (or `max`). The token is entered
> at a hidden prompt or on standard input with `--token-stdin`. Only the worker reads the provisioned token. It holds
> the bytes to copy them into each run or preflight, the copy deleted afterwards, and in memory for that run's lifetime to
> withhold any run of 12 or more of its characters from the run's output and its probes. While the token is provisioned,
> the daemon may read it to withhold it from its own log at any time. The worker records, prints and passes on nothing
> of those bytes. A run's copy lives in its fresh configuration directory and is removed at settlement.
>
> Every setup-token run requires a format-3 qualification that names the account type as the operator's statement,
> including runs using the shipped baseline. Upgrade a format-2 estate to format 3 or use a provisioned credentials file.
>
> In JSON, `worker configure --launcher claude-code` returns `null` when launcher defaults are unset and there is no
> setup-token provision. Both that command and `worker configure` include `setupToken` only when a token is provisioned.
> The field reports `provisioned`, `importedAt`, `accountType`, `accountTypeSource`, `expiresAt` and any `problem`.
>
> `worker qualify --check --launcher claude-code` establishes the inventory with a temporary copy of the provisioned sign-in,
> reports the sign-in form and qualification status of the installed version, and checks the configured model selector for
> blocked terms. It needs no principal and creates no record. `doctor` also reports the version difference.
> The [CLI guide](cli.md#provisioning-and-checking-claude-code-095) gives the commands.

## docs/limitations-and-platforms.md

### After the paragraph beginning "Codex receives a fresh"

> From 0.9.5 (FIX-167), Claude Code on macOS can use the same run-specific credentials file as on Linux and Windows.
> The worker can prepare it from a provisioned setup-token sign-in. That form carries no account type and the operator
> states Pro or Max when importing it. The macOS probe observed that a fresh configuration never reached the keychain sign-in.
> The worker's platform stand-ins use only files and do not change the keychain. Preflight itself makes no inference call.
>
> Only the worker reads the provisioned token. It holds the bytes to copy them into each run or preflight, the copy
> deleted afterwards, and in memory for that run's lifetime to withhold any run of 12 or more of its characters from
> the run's output and its probes. While the token is provisioned, the daemon may read it to withhold it from its own log
> at any time. The worker records, prints and passes on nothing of those bytes.
>
> The value comparison can leave fragments of 11 characters or fewer, including an 11-column box wrap. A prefix-free
> body can remain visible with a zero-width space, soft hyphen, NUL or combining mark such as U+0301 every 11 characters
> or fewer. The comparison can leave text in escapes it does not decode (octal, `\u{..}`, `\U` and quoted-printable
> `=XX`) or in transformations it does not undo (case changes, reversal, Base64 and hex). When the worker has only shape
> checks, decorated continuations, non-whitespace splits and prefix-free fragments can still pass. Shape checks recognize
> a doubled backslash, caret or backtick before a newline inside the prefix.
>
> On Windows and Unix, someone with write access to the Vericairn home can swap the `worker` directory before the
> removal command opens it.

## docs/api-compatibility-0.9.5.md

### Under the 0.9.5 changes

> FIX-167 adds the optional `login` declaration to format-3 `harness-qualification` records for Claude Code setup-token
> sign-in. Readers before 0.9.5 refuse records carrying this field. Upgrade readers before recording or sharing a
> setup-token qualification.
