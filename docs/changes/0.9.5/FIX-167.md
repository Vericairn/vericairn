# FIX-167: Claude Code uses a provisioned setup-token sign-in

## docs/operator-guide.md

### In "18. Routing, asks and the worker", after the paragraph beginning "The person must hold the operator role"

> From 0.9.5 (FIX-167), an operator can generate a headless sign-in with `claude setup-token` and import it using
> `worker configure --launcher claude-code --import-setup-token --account-type pro` (or `max`). The token is entered
> at a hidden prompt or on standard input with `--token-stdin`. The worker gives each run a copy in a fresh configuration
> directory and removes it at settlement. Every setup-token run requires a format-3 qualification that names the
> account type as the operator's statement, including runs using the shipped baseline. Upgrade a format-2 estate
> to format 3 or use a provisioned credentials file.
>
> `worker qualify --check --launcher claude-code` establishes the inventory with a temporary copy of the provisioned sign-in,
> reports the sign-in form and qualification status of the installed version, and checks the configured model selector for
> blocked terms. It needs no principal and creates no record. `doctor` also reports the version difference.
> The [CLI guide](cli.md#provisioning-and-checking-claude-code-095) gives the commands.

## docs/limitations-and-platforms.md

### After the paragraph beginning "Codex receives a fresh"

> From 0.9.5 (FIX-167), Claude Code on macOS can use the same run-specific credentials file as on Linux and Windows.
> The worker can prepare it from a provisioned setup-token sign-in. That form carries no account type and the operator
> states Pro or Max when importing it. The macOS probe observed that a fresh configuration never reached the keychain sign-in.
> The worker's platform stand-ins use only files and do not change the keychain. Preflight itself makes no inference call.
