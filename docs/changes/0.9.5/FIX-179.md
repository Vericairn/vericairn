# FIX-179: Standing occurrences use typed permitted paths

## docs/operator-guide.md

### In "Standing agents (0.9.4)", after the paragraph beginning "From 0.9.4 a standing agent keeps working"

> From 0.9.5 (FIX-179), an occurrence's assignment takes its permitted paths from the flow step's `paths`, the goal's repeatable
> `--flow-path` patterns and the `path:` entries in the work order revision named by the goal. Each supplied list limits the
> brief, and later revisions of the order can only narrow its paths. Goals recorded earlier keep using their explicit `path:`
> entries within those limits. Proposal, activation, resume and dispatch to an agent refuse with `flow.permitted-paths` when no
> interpretable pattern fits. `goal show`, `goal next`, `goal due` and `status` warn when an active standing goal lacks matching
> paths for an agent. For an order with only prose in `scope`, set paths on the step or goal, or revise the goal to name an order
> revision with explicit `path:` entries.
>
> A held assignment must fit the current paths before it can run, and `goal next` reports when the next assignment no longer
> fits. An eligible person can carry it with `work takeover`. If the brief already carries path patterns, a goal revision can
> clear the path refusal by supplying typed declarations that cover all of them.

## docs/api-v1.md

### After the table containing `POST /v1/goals/{id}/activate`

> From 0.9.5 (FIX-179), a standing goal proposal can set `plan.standing.paths` to repository-relative patterns. The occurrence's
> assignment brief derives `permittedChanges` using those patterns, the flow step's `paths` and the named work order revision's
> explicit `path:` entries, with each source limiting the result. Proposal, activation, resume and dispatch to an agent refuse
> with `flow.permitted-paths` when no interpretable pattern fits. Run admission checks held assignments against the step's
> current bounds. Path refusals appear in `standing.pathRefusals` in the goal view and the `/next` response, in `pathRefusals`
> in the `/due` response, and in `standingAgents[].pathRefusals` in status. The `/next` response can also report a held assignment
> that no longer fits.

## docs/api-compatibility-0.9.5.md

### Under the 0.9.5 changes

> From 0.9.5 (FIX-179), proposing, activating or resuming a standing goal is refused with `flow.permitted-paths` if an agent
> work step would receive no permitted path pattern. Earlier builds accepted such goals. An already active goal relying only
> on prose scope is refused with the same code when its next step would dispatch to an agent. Inspect `goal show` for the warning
> before taking that step. Add compatible typed paths to the flow step or goal, or revise the goal to name an order revision
> with explicit `path:` entries.
>
> `plan.standing.paths` is a new goal plan key. Released standing-goal readers such as 0.9.4 report an estate validation error
> for a record containing it and refuse to take goal steps while that error remains. Upgrade readers before recording a goal
> with this key.
