# FIX-180: The runtime service carries its Vericairn home

## docs/operator-guide.md

### In "11. The daemon", after the paragraph beginning "`runtime serve` runs the daemon in the foreground"

> From 0.9.5 (FIX-180), `runtime install` captures the effective Vericairn home in the service unit. Its label includes the estate and a hash of the home, so installations for different homes have distinct names. For an existing home, symlinks, Windows junctions, and case or Unicode variants that resolve to the same directory share the label. A macOS firmlink spelling through `/System/Volumes/Data` and a Linux bind mount each get their own label. `runtime install --plan` shows the captured home.
>
> `runtime status` looks for the estate's endpoint in the selected Vericairn home. It shows the serving daemon's home as `home` in text or `vericairnHome` in JSON. When an older daemon omits its home, status reports the home that contains its endpoint file. If that endpoint answers and names another home, status exits with an error and names both homes. When no daemon answers, text status names the home it checked.
>
> A service installed before 0.9.5 continues to use the default home. When `runtime install` finds that service on the default home, it names the old label and asks you to uninstall it first. Uninstall on the default home removes the old and current labels when present. It reports each label removed, as a list in the `uninstalled` field of `runtime uninstall --json`.
>
> To move a service to an estate's own home, run `vericairn --estate <clone> runtime uninstall` with `VERICAIRN_HOME` unset. Then set `VERICAIRN_HOME` to the estate's home and run `vericairn --estate <clone> runtime install --plan` and `vericairn --estate <clone> runtime install` with the same setting. Use that home for subsequent status and uninstall commands for this service.

## docs/api-v1.md

### In "One owner", after the paragraph beginning "where `<key>` is `local`"

> From 0.9.5 (FIX-180), the endpoint file also carries `vericairnHome`, the absolute path of the home the daemon opened. Older daemons omit this field. For an answering endpoint without the field, `vericairn runtime status` reports the home that contains the endpoint file. If the endpoint names a different home, the command exits with an error that names both homes.

## docs/api-compatibility-0.9.5.md

### Under the 0.9.5 changes

> From 0.9.5 (FIX-180), `runtime uninstall --json` returns `uninstalled` as an array of the service labels removed. It is empty when nothing was removed. In 0.9.4, the field was a string naming the service label.
>
> New service labels append a SHA-256 hash of the canonical Vericairn home path to the estate-based label. Scripts can read the label from `runtime install --plan --json` or the `installed` field of `runtime install --json`.
>
> The service plan, daemon endpoint file, and `runtime status --json` add `vericairnHome`. It is the absolute home path. Status uses the home that contains the endpoint file when an older daemon omits the field, and returns null when no daemon answers.
>
> `runtime status` exits with status 2 and names both homes when an answering endpoint reports a different home. `runtime install` refuses to install on the default home while that estate's legacy service is present, and names the legacy label to uninstall.
