# FIX-169: The command line refuses clearly when the enclave helper is older than itself

## docs/operator-guide.md

### In "3. Principals, devices and admission", after the paragraph beginning "**Custody.** A new device gets the strongest custody"

> From 0.9.5 (FIX-169), the `vericairn-enclave` helper and the command line come from the same release archive, and the command line
> checks that before it signs. Before its first signature with a Secure Enclave key, and before it makes one, it asks the helper for its
> version and the commands it serves (`vericairn-enclave version`). A helper that serves no `sign-record`, or whose version is older than
> the helper version the command line was built with, is refused before anything is signed or asked of you: the refusal names the
> helper's version, the command line's and the helper version it needs, says that the helper comes from the same release archive as the
> command line, and ends "Nothing was signed." A helper from before 0.9.5 answers with its usage line instead of a version; one that also
> lacks `sign-record` comes from a release before 0.9.4. Up to 0.9.4 a command line beside an older helper failed every Secure Enclave
> signature with `the device's key store refused to sign, InvalidOperationException` and wrote nothing. On a Mac, `vericairn doctor`
> prints a `helper` line after `enclave`, and `doctor --json` a `helper` probe: the helper's version beside the command line's and the
> helper version it expects, flagged `mismatch` when the helper is older, newer or lacks a command. A helper that is beside the command
> line but cannot be started, such as one without execute permission, is refused the same way, as one that did not answer, and
> `devices create` refuses before it makes a key rather than taking another custody. To recover, put the `vericairn-enclave` from the
> archive the command line came from beside it and run the command again; keys stay where they are.

## docs/limitations-and-platforms.md

### In "Platforms and the release workflow", after the paragraph beginning "The archives are self-contained .NET applications"

> From 0.9.5 (FIX-169), the macOS archive's `vericairn-enclave` reports a version, which the command line compares with the helper
> version it was built with before it signs. That version names the release whose helper it is, and changes, with the command line's,
> only in a release that changes the helper, so a later release's command line can expect the same helper version as an earlier one, and
> `doctor` then shows no mismatch for a helper taken from that earlier archive. The check reads the helper's own answer and is no
> signature check: a development build honors `VERICAIRN_ENCLAVE_HELPER`, and a helper built from the same source answers the same.
> Helpers before 0.9.5 report no version: the command line tells them apart only by the commands their usage line lists, so it names
> their release as before 0.9.4 or before 0.9.5, not exactly.
