# FIX-174: An upgrade's restore point holds a populated live store, or the upgrade refuses

## docs/operator-guide.md

### In "The restore point and the way back (0.9.4)", after the paragraph beginning "When you apply it, the upgrade first records a restore point"

> From 0.9.5 (FIX-174), the restore point exports the live store from its file on disk, whichever runtime applies the upgrade. In
> 0.9.4, upgrading a repository-synced estate from the command line with no daemon serving it kept no live store: that command opens
> the estate read-only, and the export came from an in-memory stand-in, which wrote no file. The records themselves stayed in the
> repository, from which the previous release rebuilds its index. Every SQLite database beside the live store, such as the daemon's
> event journal `events.db` and a local-only estate's `objects.db`, is exported the same way, as one file read through SQLite, never
> as its files copied while a runtime holds them open. Before the upgrade writes anything, each copy must exist, pass SQLite's
> integrity check and hold as many rows in each table as the database it copies. When one does not, the upgrade, one-way or not, is
> refused with nothing changed. The message names the database, what failed and how to proceed. The copies are made while the upgrade
> holds the clone's writer lock, `live.lock`, alone, as `vericairn estate cache rebuild` does, so no writable session opens until the
> restore point is recorded. While a daemon, a run's MCP server or another command has the estate open for writing, the upgrade is
> refused with nothing changed: run it through the daemon serving the estate, or after stopping it. For a damaged repository-synced
> live store, rebuild it with `vericairn estate cache rebuild` and run the upgrade again. A damaged search index can be moved aside
> with its sidecars and rebuilt with `vericairn search index --rebuild`. The way back names each database's `-wal` and `-shm` files
> to remove before you copy the exported state back, and the live store too when the clone kept none before the upgrade: the previous
> release builds it again from the repository.

## docs/limitations-and-platforms.md

### In "Restore points, observers and the stop drill (0.9.4)", after the item beginning "An upgrade's readability check (FIX-145)"

> - From 0.9.5 (FIX-174), the restore point is recorded while the upgrade holds the clone's writer lock, `live.lock`, alone, as `vericairn estate cache rebuild` does. Every writable session of 0.9.2 or later holds that lock shared while it is open, so the upgrade is refused, with nothing changed, while a daemon, a run's MCP server or another command has the estate open for writing, and no such session opens until the restore point is recorded. A writer that honours the lock therefore cannot change the live store, a database beside it or any other file there during the copy. The lock is advisory: a process that writes the clone's state without it, such as one of a release before 0.9.2, which takes no such lock, or a tool of your own, is not held off. For such a process the export has a second line, which detects some changes and not others. A database that a connection holds open, with its `-wal`, `-shm` or `-journal` file beside it, is read through SQLite in one snapshot, which a writer using SQLite's own locking cannot tear. A database with none of those files is read as an immutable file, which takes no lock and creates nothing beside it, and after copying, the upgrade refuses if a sidecar appeared or the source's size or modification time changed. That detects a writer that still has the database open when the copy is checked, and one that opened and closed it during the copy only when its write changed the size or the modification time. SQLite rewrites pages in place, so the size seldom changes, and a write in the same timestamp tick as the database's previous write is not detected: on a volume with whole-second timestamps, such as HFS+, or with a clock that advances in steps of milliseconds, a copy that mixes rows from before and after such a write can be kept. A write that changes a page while it is read may instead make SQLite report the database as damaged, and the upgrade is refused. A read-only command on a local-only estate that opens its live store or object store during the copy leaves a `-wal` and `-shm` beside it, so the upgrade is refused as changed; retry it. Each copy must also pass SQLite's integrity check and hold as many rows in each table as the database did in the snapshot it was copied from; those checks find damaged pages and missing rows, not rows from two moments. Files beside the live store that are not databases, such as `observers.json`, are copied as they are, with no check of their own. A repository-synced clone that only read-only commands have opened keeps no live store on disk, so its restore point holds none.
