# FIX-174: An upgrade's restore point holds a populated live store, or the upgrade refuses

## docs/operator-guide.md

### In "The restore point and the way back (0.9.4)", after the paragraph beginning "When you apply it, the upgrade first records a restore point"

> From 0.9.5 (FIX-174), the restore point exports the live store from its file on disk, whichever runtime applies the upgrade. In
> 0.9.4, upgrading a repository-synced estate from the command line with no daemon serving it kept no live store: that command opens
> the estate read-only, and the export came from an in-memory stand-in, which wrote no file. The records themselves stayed in the
> repository, from which the previous release rebuilds its index. Every SQLite database beside the live store, such as the daemon's
> event journal `events.db` and a local-only estate's `objects.db`, is exported the same way, as one file read through SQLite, never as
> its files copied while a runtime holds them open. Before the upgrade writes anything, each copy must exist, pass SQLite's integrity
> check and hold as many rows in each table as the database it copies. When one does not, the upgrade, one-way or not, is refused
> with nothing changed, and the message names the database and what failed; when a repository-synced estate's live store itself cannot
> be read, rebuild it with `vericairn estate cache rebuild` and run the upgrade again. The way back names each database's `-wal` and
> `-shm` files to remove before you copy the exported state back, and the live store too when the clone kept none before the upgrade:
> the previous release builds it again from the repository.

## docs/limitations-and-platforms.md

### In "Restore points, observers and the stop drill (0.9.4)", after the item beginning "An upgrade's readability check (FIX-145)"

> - From 0.9.5 (FIX-174), the restore point reads a database beside the live store that has no `-wal`, `-shm` or `-journal` file as an immutable file, which creates nothing beside it: such a database was closed cleanly and no runtime holds it. Like a read-only command's snapshot of the live store, this assumes that no other runtime on the machine writes the clone's state while the upgrade runs. A database a runtime holds open is read through SQLite in one snapshot. A repository-synced clone that only read-only commands have opened keeps no live store on disk, so its restore point holds none. The export's check compares row counts and SQLite's integrity check, not each row's bytes.
