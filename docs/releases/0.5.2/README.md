# Vericairn 0.5.2

Vericairn 0.5.2 is the first published release that writes record format 2. It carries the work built as 0.5.0 and again as 0.5.1, both withdrawn before acceptance and publication after their independent reviews: 0.5.0's first authority bound signed admissions only, so that while a charter left signatures optional, the default for every new estate, an unsigned admission still admitted a device, and 0.5.1's correction rested on the format each record claims, so that an unsigned admission written in format 1, or dated before a required-signature policy, still counted. In 0.5.2 the rule rests on a signature: in an estate at record format 2 an admission, admitting or revoking, counts only when it is signed, or when the operator's signed move to format 2 lists it, whatever format or date it states. It brings the identity work of milestone M3 that needs no second machine (key custody, device identity, the first authority and emergency access) and the foundation of living documents. It follows 0.4.2 and is built from main under the operator's decisions 01M4YBR5PG3AAZ8WAKZZ0R10K1, 01M4YSTRMRCFFNYQCANY86QG8E, 01M4YZECP84H43ZMK607J39ZN3 and 01M4ZPEZZG2A6K96V83DXBSSRW. Goals' runtime, pairing and local-network connections are release 0.6.0, and Remote is release 0.7.0.

- **Record format 2** (GOAL-01). A record states the format it was written in and is validated under that format's rules, so nothing already written changes. Format 2 carries goals, goal statuses, rosters, asks, possibilities, the discharge of a decision's obligations, credential references, platform qualifications and the living-document records. A decision states how much rides on it and what it does not authorize, and a revision of it keeps the operator's words. A grant can expire, and authority is judged at the time each record was authored. `vericairn estate upgrade --to 0.5.2` moves an estate to format 2 in one reviewable commit that rewrites no record; when the estate holds admissions recorded without a signature, the operator, or an administrator, signs the move, which lists them. 0.5.2 validates the goal records; carrying a goal out is the work of 0.6.0.
- **Key custody and device identity** (ID-01). A new device gets the strongest custody its machine offers: the platform key store (CNG) on Windows, the Secure Enclave on a Mac that has one, through the `vericairn-enclave` helper the macOS distributables carry, the secret service on Linux where one runs, and otherwise an owner-only file. A person's device needs its owner's presence (Touch ID or the login password) at every signature wherever its custody enforces it; an agent's device never claims presence. A device keeps its identity across renames and key rotations, and a rotation signed by the old key and the new one moves a key into other custody. The estate's first authority, the operator's first device admitting itself, is the only self-admission accepted, and in an estate at record format 2 every other admission and every revocation counts only when it is signed by a device already admitted, or listed by the operator's signed move to format 2, whatever the charter's signature policy and whatever format or date the record states; 0.4.2 and earlier accepted any self-admission by the operator. The operator's recovery device, whose key is kept offline in a file encrypted under a passphrase, is the way back in when every other device is lost.
- **Living documents** (DOCS-03). An estate declares the documents whose claims follow facts that change, with the triggers that make each due: its covered paths changed, a release, an upgrade, a decision that names it, or an accepted work order. Each trigger has a level: remind, warn, or refuse, which refuses the product's next release submission. `vericairn status` lists every document that is due and why; a review clears one at its exact content once its declared checks pass; generated regions are held to their generators; a document in another repository is read at a commit through the software pack. Workbench's Documents page (Ctrl+Shift+D) and the MCP tools `documents_due` and `document_review` reach the same.

It also carries the work of DOCS-02, merged after the 0.4.2 release commit: the README names no release as current, and the agent orientation file is held to its generator by `vericairn mcp orientation --check` and a test.

An estate is the continuing body of work and responsibility behind a venture, held as append-only, content-addressed, signed records: principals and devices, decisions, work orders and briefs, assignments, attempts and results, reviews and acceptances, releases and migrations, resources, verifications, operations and now living documents. The tool renders the estate's state from those records, refuses records that would make the estate invalid, and runs the loop Vericairn builds itself with: work under the pinned release, release the next version through a provider with intent recorded before effect, accept it from the recorded evidence, upgrade the estate, repeat.

After this set was frozen, release 0.5.2 goes through the steps its release record and the estate record as they happen: the release workflow builds it from the commit the record names with its tests on Ubuntu, macOS and Windows and holds it as a draft; the candidate is reviewed independently; the operator accepts the exact candidate from the recorded evidence, and it is published by hand. This set states those steps as what follows the freeze, not as facts it could know. It is an unsigned developer build; verify downloads by checksum (see `install.md`).

## This documentation set

This set was produced on October 15, 2026, before the release build, as the convention in `docs/releases/README.md` requires: the references and the manifest were generated by the build tooling (`vericairn-docs generate`) from the 0.5.2 build, the release notes from the Vericairn estate's records since the 0.4.2 publication, and the guides written against the same build, whose journeys were run on it in a scratch estate. The release's own record (commit, workflow run, artifacts by hash) is written when the draft is observed and lives in the estate, not in this frozen set; `limitations-and-platforms.md` states what was known before the build. The release workflow refuses to draft a release whose set is incomplete or disagrees with the build, and ships the set as `vericairn-0.5.2-docs.zip`. The set is frozen with the release; corrections go into the next version's set.

This set corrects the operator's guides of the 0.2.0 to 0.4.2 sets, which said that `estate init` writes three records and that `estate check` then reports three: it writes two records, the operator principal and the charter, beside the manifest, which is not a record, and both 0.4.2 and 0.5.2 report two. It also corrects the 0.5.0 and 0.5.1 sets, frozen with those withdrawn builds, which stated the first authority without the conditions their builds had, and section 8 of the 0.4.2 guide, which said that earlier builds do not accept a release profile: published releases before 0.4.2 refuse one, while the withdrawn 0.4.0 and 0.4.1 builds accept it.

## Are you running 0.5.2?

```sh
vericairn version
```

prints `0.5.2+<commit>`, the commit the release record names. `vericairn doctor` prints the version, the runtime, whether git and the .NET SDK are present, the estate it sees, the key custody a new device gets by default in the estate it sees, whether Secure Enclave custody is available on a Mac, the record formats the build reads and writes, and whether a daemon serves the estate. Workbench shows the estate's pinned release and the runtime's state in its target bar.
