# Workbench

`vericairn-workbench` is the desktop: a client of the daemon through the SDK and the runtime's manager, never its host. It opens no live store and evaluates no authority; everything it shows comes from the runtime's responses, rendered with the same state language as the command line (the golden file at `docs/state-language.json`, checked by tests against the presentation library and the runtime's own strings).

## What exists after WB-03

- The shell (WB-01): primary navigation on the left (Home, Work, Products, Releases, Runtime, Records), documents in the center as tabs, the inspector on the right, the activity log at the bottom, the target context on top (estate, pinned release, runtime state, the acting principal by its current name with the device the runtime signs with, freshness) and a status line. Panels resize with splitters and hide, show and reset with keyboard alternatives; the layout is a per-user preference saved under the Vericairn home.
- First run and returning user: open an estate's root (recent estates are remembered); a directory without `estate/manifest.json` is refused and nothing is created; when no daemon answers, Workbench starts one through the command line beside it, waits for that command to finish (never for the end of its output, which 0.3.0 did and so never opened the estate on a first launch), and reconnects.
- Home: attention items of the six kinds, derived from the status document alone, each with why it matters, its state, freshness and the next action; selecting explains, Enter opens the subject. A result awaiting review opens in the review workspace.
- Acting principal: chosen among the admitted devices held on this machine (the target bar's chooser), or named with `--as` for a principal whose device the runtime holds. Without one, every write surface says so before any request is sent; Workbench never evaluates authority itself.
- Products: the product records with their editions and surfaces. Projects are not a record type of format 1; the page says so instead of inventing them.
- Work order pages: the brief (key, title, kind, intent, exit question), the assignments with their attempt counts and latest results, the observation, and the actions that start the loop (assign, review the selected result, compare with the earlier revision). Open one by key or id with Ctrl+G.
- Assignment pages: the brief as delegated, the assigning note, and the attempts with their workspace, note and result (outcome, summary, state); Enter on an attempt opens its result for review.
- Assignment composer: the brief's fields, one list entry per line; nothing is sent until "Send the assignment", the runtime validates and signs, and a refusal is shown with every finding.
- Result inbox (Ctrl+I): the results awaiting review across the estate, each a claim to inspect; Enter opens the review workspace.
- Review and decision workspace: the exact result (outcome, summary, outputs, evidence, checks, limitations, unresolved effects, next step), the reviews on record, a review draft (outcome, summary, findings) and an acceptance draft whose basis is the checked reviews. Both are sent through the API pinned to the subject's hash; the independence and self flags the client will declare are derived from who authored the subject and shown, and the runtime checks them.
- Prepared actions: a draft is pinned to the subject revision and to the facts on record about it when it was prepared; returning to it re-fetches both and reports reusable (nothing changed), needs review (new records about the subject appeared; the draft is kept, nothing is sent) or withdrawn (the subject was superseded or is gone; the draft stays readable, nothing can be sent). A write of the workspace's own re-pins it, since the person has just seen that record.
- Comparison views: a record beside the revision it supersedes, with the line difference between them; the raw sides stay readable.
- Runtime workspace (Ctrl+Shift+U): the daemon's state, where it is, what it reports about itself, start and stop, the install plan, and install and uninstall of the per-user service through the command line beside Workbench; the plan is shown before either is possible. The daemon's state is always in the target bar.
- Release workspace (Ctrl+Shift+E): a provider's intent-then-effect flow through the same runtime operations the command line uses (`POST /v1/releases/submit` and `observe`). The provider list is what the runtime can reach (`GET /v1/providers`); the product's declared provider is selected, and for a product that declares none nothing is selected until the person chooses. The form shows one field per setting the selected provider declares, filled with the product's declared values, and an empty field means the provider's default, which its label names. Submit records the intent before the dispatch, observe records the run's outcome, the candidate with every distributable by hash and later the observed publication, each destination shows preparation, submission, external review and observed availability separately, Enter on a destination opens its candidate in the review workspace for acceptance at its exact hash, and the operator's manual publication command is shown and never run. A second submission under the same identity is refused exactly as on the command line.
- Documents page (Ctrl+Shift+D): each declared living document with its state (current, due at its level, or unavailable), every trigger newer than its latest clearance, and that clearance (`GET /v1/documents`). A review of the selected document is sent with Ctrl+Enter (`POST /v1/documents/{id}/reviews`): the outcome, what was checked, a commit for a document of another repository, and findings. The runtime reads the content, records what the review answers and runs the declared checks; the page decides neither independence nor clearance, and a refusal shows every reason.
- Keyboard-only: every request of the open document is sent with Ctrl+Enter (assignment, review, release submission, document review) or Ctrl+Shift+Enter (acceptance, observation); Ctrl+Shift+A opens the composer for the open work order; opening a workspace lands the keyboard in its first field, and Tab moves through the form.
- Theme: the brand's token contract is bound in one resource (`Theme.axaml`): eight color roles in light and dark variants, four type roles, three scale roles and two motion roles. The first values were adopted on October 14, 2026 (design/brand.md revision 2): Inter for title, heading and body and JetBrains Mono for identifiers, both bundled under the SIL Open Font License, one accent blue, one attention amber used only for the attention kinds, neutral surfaces and outlines. The probe measures the contrast ratio of every pair the roles form in both variants (text and muted text on the surfaces at 4.5 or better, outlines at 3 or better) and reports it beside the target sizes. The mark and the wordmark (`brand/`) appear on the arrival page; the shell binds roles, never values.
- Records: open any record by id.

## Keyboard

Ctrl (Cmd on macOS) with 1, 2, 3, 4 focuses navigation, documents (or the attention list on Home), the inspector and the activity log. Ctrl+Shift+L, R, B toggle the navigation, inspector and activity panels; Ctrl+Shift+0 resets the layout. Ctrl+O focuses the estate path; Ctrl+G the record or work-order id; Ctrl+I opens the result inbox; Ctrl+Shift+E the release workspace; Ctrl+Shift+U the runtime workspace; Ctrl+Shift+D the Documents page; Ctrl+Shift+A the composer for the open work order; Ctrl+Enter and Ctrl+Shift+Enter send the open document's requests; F5 refreshes; Enter opens the selected item (an attention item, an inbox row, an assignment, an attempt's result, a release destination's candidate); Escape returns to navigation. The Work and Runtime menus carry the same actions. Every pointer arrangement has one of these.

## Running it

```sh
vericairn-workbench --estate <estate root> [--as <principal id>]
```

`--as` names the principal Workbench writes as. The selector in the target bar then shows that principal's admitted device held on this machine, the one the runtime signs its records with, and choosing another device in the selector makes that device's principal the acting principal. When the named principal has no device held here, the target bar says so: its writes are refused where the estate requires signatures, and written unsigned where it does not. (Release 0.3.1 showed such a principal under its first revision's name beside the first device held on the machine, whoever's it was; the records were still authored and signed correctly.)

The command line is found beside the executable, through `VERICAIRN_CLI`, or on the path; Workbench uses it to start and stop the daemon. The accessibility probe measures every focusable target of the shell at compact density and writes an observation for the platform obligations:

```sh
vericairn-workbench --probe <file.json> --cell "macOS native" [--virtual] [--estate <root> --open products|inbox|release|runtime|<work-order key>]
```

With `--estate` and `--open`, the named workspace is open when the measurement is taken, so each screen's targets are measured on the native desktop, not only the shell's.

## Limitations after WB-03

Keyboard-only journeys of the work loop and the release flow run headless on the three platforms; a native keyboard-only run with a screen reader needs a person on each desktop and is recorded per cell in the platform obligations, as are the accessibility measurements. Workbench ships as an unsigned developer build per platform beside the command line, with no bundle, installer or signature. Projects wait for the record format to define them. The comparison is a line difference of canonical JSON, not a field-aware merge. Docking is panel placement with keyboard alternatives, not free drag-and-drop of every panel.
