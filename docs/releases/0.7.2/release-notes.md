## Security

Vericairn 0.7.2 fixes an integrity defect in restoring an estate export, present in every published release from 0.1.0 through 0.7.1. Verification checked each path in the export's inventory against only the first archive member with that name, and restore then wrote every member. An archive with a second member under an inventoried name therefore passed verification, and restore wrote that member's unverified bytes over the verified ones while still reporting a verified export. Restore also reopened the archive after verifying it, so a file replaced between verification and extraction was never checked.

The exposure matters when you restore an export that someone else could supply or alter, or that another local process could replace during the restore. It needed no admitted device or signing key. It did not forge record signatures or restore signing authority, but a substituted document or other file could pass as verified.

In 0.7.2, restore refuses duplicate inventory paths and duplicate archive members, including the inventory and summary entries themselves. It also refuses unsafe relative paths, and paths that collide after the destination platform's normalization of case, Unicode and separators. It verifies and extracts from one opened archive, checks each file's size and SHA-256 against its inventory entry immediately before writing it, and never overwrites an existing file. Every restored file is now bound to the export's inventory. This does not establish who produced the export; record signatures are still validated separately.

Upgrade to 0.7.2 before restoring an export you did not produce yourself. If you restored such an export with an earlier release, restore it again with 0.7.2 and compare the results, or compare the restored files against a trusted copy.
