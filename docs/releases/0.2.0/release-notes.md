### M2-API: The daemon, the versioned API, the SDK and the CLI as a client

Result 01M4VDZQ1RRBA2NV8MGV5TQW7Z (completed), recorded 2026-10-13 20:06 UTC. The runtime is a service. Vericairn.Protocol is the single definition of the API: the operations, the request and response types, the problem codes (refused, rejected with findings, not-found, invalid, conflict, denied) and the OpenAPI document served at /openapi/v1.json. EstateService in Vericairn.Runtime is the one implementation and the only place authority is evaluated. Vericairn.Daemon owns one open estate, publishes an endpoint file beside the live store, refuses a second owner, and serves the API over a local socket (a Unix domain socket in the user's runtime directory, a named pipe on Windows) and over loopback TLS pinned to a self-signed, rotated runtime certificate where every request is signed by a device admitted now and accepted once. Vericairn.Sdk is the typed client with pinned transport and request signing. The CLI runs every estate operation through the API, the daemon's when one serves the estate and the embedded runtime otherwise, and gained runtime serve, start, stop, status, install (launchd agent, systemd user unit or Task Scheduler logon task, with --plan) and uninstall. The architecture, cohesion-contract and cli-and-sdk documents were revised where the mechanism differs: the endpoint file and the one-owner refusal, and a C# client that shares the contract's types and is checked against the OpenAPI description instead of being generated from it.

Limitations recorded:
- The estate stays pinned to release 0.1.0, which has no daemon; its everyday commands run through the API once 0.2.0 is released and the estate upgraded under M2-RELEASE. This result's evidence of the estate through the API came from the development build.
- The local-network profile with mutual authentication is milestone M3; the daemon does not yet run admitted work or supervise workers, which is milestone M4.
