## Security

Vericairn 0.9.3 corrects one weakness, in how keys in forms Vericairn does not make are read. No record, signature or authority was accepted because of it.

**A public key in an unsupported or malformed form stopped the estate check and status (presumed all releases through 0.9.2; FIX-132).** Before 0.9.3, some such keys, for example ones with curve parameters written out in full, on another named curve or with a point off the curve, made the platform or the framework's own key reader raise an error Vericairn did not handle, so one record file carrying such a `publicKey`, signed or not, made `vericairn estate check`, `vericairn status` and the runtime operations behind them fail until the file was removed, and a local-network client certificate with validity dates at the edge of the calendar made the runtime's authentication fail with an error instead of its usual refusal, which told a client whether the device it named existed; no record, signature or authority was accepted because of either. From 0.9.3 a key is read as usable only in the one form Vericairn makes, a named P-256 key with an uncompressed point, checked before any platform sees it, any other is reported with its record's findings (`device.public-key`, or `body.length` for an encoding longer than a device record takes) and verifies nothing, the runtime identity check applies the same rule, and every client certificate the device's key did not issue gets the same refusal whatever its dates; upgrade every machine that reads an estate others can add files to, and until then remove such a file to restore the checks.
