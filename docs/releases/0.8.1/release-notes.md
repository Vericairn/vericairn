## Security

Vericairn 0.8.1 corrects weaknesses that an independent security review of 0.8.0 found in four areas, and one found while making the tests independent of real time. None of them lets anyone sign a record without an admitted device or act as another principal.

**What an agent can do outside its workspace unnoticed (0.7.1 through 0.8.0).** The worker's command audit requests containment of a run when an agent's command reaches outside its workspace or toward credentials. It missed some forms: paths written with partial quoting, such as `''"$HOME"/x`; commands run inside `dash`, `ksh`, `mksh`, `ash`, `yash`, `posh` or `eval`; and a recursive copy of the home's `estates` directory, which holds each estate's local stores. In 0.8.0, settlement also applied the ignore rules as the run left them, so an agent that added an ignore rule could hide a file it changed outside its brief, and a nested repository inside an ignored directory went unseen. In 0.8.1 the audit resolves paths as the shell does, inspects those shells and `eval`, warns about any program or shell it cannot inspect, and treats those copies as critical. Settlement applies only the run's starting ignore rules, reports a changed or added ignore file as a change outside the brief, and marks the audit incomplete when it finds a nested repository. The audit still observes reported commands and is not a sandbox: run agents under a separate operating-system user, as the guides describe.

**Observation pipes on Apple silicon Macs (0.6.1 through 0.8.0).** On macOS on Apple silicon, the worker did not mark the pipes it uses to observe a run's output as closed when it starts another program. A process the same worker started at the same time, such as another run's agent, could inherit those pipe ends, and so read or write that run's observed output or keep its stream open after the run ended. In 0.8.1 the worker marks them correctly on every platform.

**Who may change a product's push and merge rules (0.8.0).** A principal allowed to revise a product, such as a builder, could change or remove its checked-changes declaration, which decides how pushes and merges are scanned and checked, or move a repository's recorded location. A checked merge did not require a scan of its exact head. The secret scan used gitleaks' built-in allowlists, which skip paths such as `package-lock.json`, `vendor/` and `node_modules/`, some file types and values that look like samples. In 0.8.1 only the operator or a principal with the administer scope may change those records, a checked merge needs a scanned push of its exact head, and the scan uses Vericairn's own configuration: gitleaks' default rules without their built-in allowlists, plus nine explicit allowances, none of which exempts a path.

**Release and upgrade integrity (the release gate in 0.8.0; the upgrade from 0.1.0 through 0.8.0).** A release could proceed when a refuse-level living document in another repository could not be compared because that repository had no registered clone: the gate reported it as not compared but did not stop the release. An upgrade wrote the estate's manifest before its migration record, and not atomically, so an interruption could leave the estate at the new format without the record of its migration. In 0.8.1 that uncompared document refuses the release unless the operator signs an expiring exception for that document and version. The upgrade records its migration first, replaces the manifest atomically, and resumes after an interruption.

**How Vericairn's own releases are built (every release through 0.8.0).** The job that built and packaged a release held a repository write token for its whole run, kept that token in its checkout, and wrote the version input directly into its scripts. In 0.8.1 the packaging steps hold only a read token, every checkout drops its credentials, and inputs reach scripts only through the environment. One separate step, which checks nothing out, holds the write token to create the draft. This concerns how Vericairn's releases are produced, not software you have installed.

Upgrade to 0.8.1 before running agents through the worker on an estate you care about, and restart any running worker, since a worker keeps the audit of the release it runs. If agents ran under 0.8.0's worker, review their retained branches for changes to `.gitignore` files or `info/exclude`. If a principal other than the operator changed a product's checked-changes declaration under 0.8.0, review that change.
