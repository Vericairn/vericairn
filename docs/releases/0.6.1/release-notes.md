## Security

Vericairn 0.6.1 fixes an authorization defect present from 0.2.0 through 0.5.2. The daemon checked that a loopback API request was signed by an admitted device, but did not bind the requested action to that device's principal. A process on the runtime's machine with access to an admitted device key could ask the runtime to act as another principal, including the operator. This could produce unauthorized records, assignments, and device admissions or revocations, subject to the operation's existing validation and signing requirements.

The exposure matters most when agents or other less-trusted processes run under a different operating-system user on the runtime's machine. Processes under the runtime's own user can already use its keys held without presence. Keys that require their owner's presence still prompt when used to sign; this defect does not bypass that protection.

In 0.6.1, every device-authenticated request, on loopback and on the new local-network profile, is bound to the principal of the device that signed it. Every served operation has a declared scope, and machine-local operations are refused over the local network. The owner-restricted local socket continues to trust the operating-system user.

Upgrade to 0.6.1 and restart the runtime. If less-trusted local processes could sign requests with an admitted device while an affected daemon served loopback, also review records written through the API during that period, especially authority, assignment, decision, and device-admission records. A valid record signature alone does not establish that its principal requested the action.
