# Vericairn roadmap

This page shows where Vericairn is headed, release by release. Everything after the current published
release is planned, not promised, and has no dates. Each release's notes and documentation set are the
record of what shipped.

## 0.8.2 — current published release

0.8.2 follows 0.8.0 and carries the work of the 0.8.1 candidate, which was withdrawn before publication,
with a correction that lets the macOS and Linux command lines start other programs. Commands record exact
document revisions and observe NuGet publication, listing and deprecation, and the packages carry the
cairn mark as their icon. The worker's command audit and settlement, the release gate, the rules for
checked pushes and merges and the estate upgrade are hardened, as the release notes' Security section
describes. Every client reports a record as stored, not refused, when publishing its readable companions
was interrupted, and the estate check ignores top-level files the repository's own ignore rules exclude.
A retained release basis stays small however large the estate grows. Vericairn's MCP server is listed in
the official MCP Registry and among nuget.org's MCP servers. One known issue: each platform's archive
carries a separately compiled build of the same libraries, so a policy basis differs by platform
([issue 184](https://github.com/Vericairn/vericairn/issues/184)); 0.8.3 fixes it. Its
[release notes](docs/releases/0.8.2/release-notes.md) and [documentation set](docs/releases/0.8.2/README.md)
describe what shipped and its limits.

## 0.8.3 — planned

A first estate needs no hand-written JSON: `estate init` pins the build you run, a new command creates a
work order from its options, and an estate can pin and upgrade to the published Vericairn release it
depends on. Living documents show the same due state everywhere the release gate does. A release can be
checked against the whole gate before it is submitted, a candidate withdrawn and a plan moved to another
version with single commands, and every platform's archive carries the same library builds. CI runs each
platform's published command line, and after an upgrade the command line says plainly when an older
background runtime is still serving the estate.

## 0.8.4 — planned

Reusable templates give documents, roadmaps, communication, context, commits and reviews consistent
sections and checks. Saved prompts, each with a title, description, category, placeholders and the roles
it suits, can be shared across an estate, kept as personal favorites, and used with new agent runs,
assignments and answers to an agent's questions, from the command line or as prompts in coding agents that
support them. An optional efficiency adapter helps reduce eligible agent context, once the agent hook it
uses is designed and qualified, and a design document's revision lines are generated from the revisions
the estate records. The operator closes finished work in one signed action, and release review briefs,
decisions and the documentation pass after each release come from the records. This release's cycle also
designs release lines and channels (long-term support, prerelease and nightly channels, release cadences
and keeping a fix's public description until its release) and progress that an agent reports when its
configuration asks for it, as an exact count, a best-effort estimate or not measurable, with a status
text. None of either design is built before it is accepted.

## 0.9.0 — planned

The Remote companion brings supervision, eligible decisions and readable records to a phone, with
handoff to the desktop for work that needs it. From Workbench or the phone, a saved prompt can be sent to a
running agent in one step; it steers the agent without widening what the agent may do.
A public example estate and app show the whole loop on GitHub, from a work order through an agent's
recorded run, review and acceptance to a release, and every release upgrades them. Every planned catalog
entry gets a community build guide, and anyone can request the implementations they need most, one
request per account, to inform what is built next. A support bundle collects what a support case needs,
with secrets and paths removed, and shows you everything in it before you share it. This release's cycle
also designs the editions and their services, the contract for foundries that start or reshape a project
with the first software foundries, and the website, web application, book, book series and world-building
domains.

## 0.10.x — planned

The first creator domains arrive in this order: websites and web applications; books, book series and
world building; courses and video, single and in series; and crowdfunding. Each first version takes the
work from drafting through templates and review to a publishable package with its metadata, such as an
EPUB and print-ready PDF or a deployable site. You publish on the platform, and Vericairn records the
publication; direct platform integrations follow. These domains ship within the Community distributable
and move to separate packages at the packages milestone below.

## Editions — planned direction

Community stays free and open source, and no Community feature will move behind payment. Standard is
planned to license the coordinated production features for one person and Pro the same features for teams
and organizations; there are no offers or prices yet. Every paid service Vericairn plans, such as hosting,
a relay for Remote, backups, managed workers or first-tier support by agents, is planned as the same
software you can run yourself at the edition that sells it. You will never be locked in:

1. Every paid service has a self-hosted path at the edition that sells it.
2. No access to your estate requires a Vericairn account; an account only pays for and manages hosted services.
3. An estate moves between Vericairn's hosting and your own in either direction without loss.
4. Paid rights are verified offline, without contacting Vericairn, and outlive its servers.
5. Ending a subscription ends only Vericairn's operation of a service, never self-hosting of covered releases or any Community right.

## Later milestones: hosted storage — planned

Today an estate's records live in a git repository beside your work, or in a store on one machine. Four
hosted options are planned, each built and qualified on its own before it is offered: a runtime on one of
your own machines, reached over your network; a runtime hosted with your Vericairn account; a shared
runtime an organization operates for its members; and managed hosting from a provider you choose.

## Later milestone: coordination, packages and websites — planned

Coordination and scheduling across work, extension packages and foundations for a package registry.
Readers for Knowledge and the catalog, and websites generated from the same records, including this
roadmap.

## Later milestone: specialist workflows — planned

Unity projects and games follow, with the further foundries, adapters and providers of the creator
domains beyond their first versions. Vericairn's catalog plans more
than 3,000 entries across creative and technical work and 27 industries, listed in the
[README](README.md#planned); each further domain is placed on this roadmap when its milestone is chosen.
